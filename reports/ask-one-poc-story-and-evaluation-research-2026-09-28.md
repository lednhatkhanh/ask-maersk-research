**Checked:** 28 September 2026. **Purpose:** evidence and proposed POC choices for the next local slide revision. This note does not estimate implementation or establish a production architecture. The five screenshots supplied in the review are visual evidence from the reviewer, not a measured usability study.

## Review decisions used in the current deck

The proposal uses a two-month POC with team size and allocations TBC. The initial source work prepares a sync of the Drupal **Insight** content type and adds eCommerce or business content approved by its owners. The customer benefit is less effort to find a source-backed answer and a clearer next action; ONE can make its published guidance more useful, increase use of digital services and reduce repetitive support effort. The reviewer clarified that ONE Live Chat already has a bot oriented to support enquiries. Ask ONE's proposed longer-term role is a broader digital-copilot entry point: booking and schedule search are concrete later service examples, and a booking agent is one possible later agent feature. ## Findings that can support the executive story

1. **The current search experience leaves a content gap.** The project reviewer describes ONE search as a text-results experience that is not set up to bring additional document sources together in one answer. Ask ONE's proposed improvement is to use approved CMS Insights, documentation and eCommerce FAQs to give a short cited answer and next action. The POC should demonstrate that journey on real tasks and measure its quality and reach; it should not promise a contact-saving figure before usage evidence exists. 2. **Live Chat already includes a support bot.** ONE directs customers with shipment-status, approval, invoice, document, and other transactional inquiries to its digital services and Live Chat. The reviewer clarified that Live Chat has a bot for support enquiries. The supplied screenshots show a country/city selection before chat and an outside-business-hours support form in one viewed route; they do not show the full bot capability or establish that every market or session works the same way. Ask ONE's proposed digital-copilot role should be explained through its own benefits and expansion path rather than a feature-by-feature comparison that understates Live Chat. The POC does not change or connect to Live Chat. [ONE advisory](https://www.one-line.com/en/local-information/id/news/access-all-one-shipping-solutions-one-ecommerce-and-live-chat); reviewer clarification and supplied screenshots 4–5, 28 September 2026.
3. **The proposed POC is a content-to-action guide.** Start with approved CMS Insights, other approved documentation, and eCommerce FAQs. Show a short answer, the source title and date, and a relevant guide or eCommerce action. If a source cannot support an answer, the POC gives a neutral fallback and existing help-page link. It does not route into Live Chat. This UX is a proposal inferred from the existing ONE content and channel mix, not an existing ONE feature or a guaranteed automation benefit. ONE's site already presents Insights and eCommerce entry points; the proposed answer would connect them for a question. [ONE homepage](https://www.one-line.com/en), [ONE advisory](https://www.one-line.com/en/local-information/id/news/access-all-one-shipping-solutions-one-ecommerce-and-live-chat).
4. **Future agents are an expansion path, not POC scope.** A later phase could connect authenticated shipment, booking, or case workflows through separately approved integrations. The first POC should remain read-only guidance and navigation; it should not claim to check private status, submit a form, or transfer a conversation to an agent before those capabilities and permissions are proved. ONE's current digital-service list demonstrates that these are separate customer tasks today. ## POC content and governance boundary

- Agree a small, representative set of **published and permitted** CMS Insights, documentation, and eCommerce FAQ pages with content owners. Record source ID, canonical URL, owner, locale/market, publication status, last approved version, and next review date. This is a proposed publication contract, not evidence that the present CMS exposes every field. Drupal core JSON:API can expose entity content through its access model; Drupal warns that filters are not access control and recommends auditing entity and field access. [Drupal JSON:API module](https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module), [filtering and access](https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module/filtering), [security considerations](https://www.drupal.org/docs/core-modules-and-themes/core-modules/jsonapi-module/security-considerations).
- Test publication, correction, locale restriction, and withdrawal. RAG Engine supports file import and deletion, and its import path can reindex a changed file; Agent Retrieval documents object create/update/delete. These API capabilities alone do **not** prove that a removed source has stopped appearing in customer answers. Measure the full source-to-index-to-answer delay and block stale citations. [RAG corpus management](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/manage-your-rag-corpus), [RAG ingestion](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/use-data-ingestion), [Agent Retrieval data objects](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/vector-search-2/data-objects/data-objects).
- Keep provenance visible. A source link should resolve to the approved page and support the **specific claim** in the answer; displaying any relevant link is weaker evidence. Google describes groundedness checks against supplied reference text, while its search evaluation separates retrieval relevance metrics from response quality. [Google grounding API overview](https://docs.cloud.google.com/generative-ai-app-builder/docs/builder-apis), [search evaluation](https://docs.cloud.google.com/gemini/enterprise/docs/evaluate-search-quality).

## How QA can evaluate the POC and continue evaluating

**Before the demo:** PO/PPO, content owners, QA, and support representatives select realistic tasks and label a versioned case set. Include Insights, documentation, FAQ, conflicting or outdated content, market-specific answers, unanswerable questions, prompt attacks, and requests for private status. For each case, record the expected approved source, acceptable answer/next action, required fallback, and severity of a wrong answer. Google recommends stabilizing evaluation data and metrics early and including adversarial cases; its search evaluation uses a reusable sample-query set for comparable runs. [Google Cloud architecture guidance](https://docs.cloud.google.com/architecture/deploy-operate-generative-ai-applications), [search evaluation](https://docs.cloud.google.com/gemini/enterprise/docs/evaluate-search-quality).

**QA review sheet:** score (a) whether a usable approved passage appears in top results, (b) answer correctness and completeness against the approved source, (c) whether each material claim is supported by its cited passage, (d) correct guide or eCommerce link, (e) safe fallback and over-refusal, and (f) task completion and time relative to current search/help. Separate retrieval scores from answer scores: Google defines recall, precision, and NDCG against labelled search results. A model judge can assist triage, but Google recommends comparing judge ratings with human ratings; human review should own the release decision. [Search evaluation](https://docs.cloud.google.com/gemini/enterprise/docs/evaluate-search-quality), [judge calibration](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/evaluate-judge-model).

**Repeatable loop:** rerun the same cases after each source/prompt/retrieval change, add cases from QA defects and consented pilot feedback, periodically sample real answers for human review, and show results by source type, market, answerability, and severity. Track content update/withdrawal propagation and regressions alongside answer quality. Google's evaluation result format supports per-case results and aggregate scores; its guidance recommends regular reruns and comparing historical search results. Exact cadence, sample size, thresholds, and access to production data require agreement during POC planning. [Google evaluation results](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/eval-python-sdk/view-evaluation), [search evaluation](https://docs.cloud.google.com/gemini/enterprise/docs/evaluate-search-quality).

## Concrete GCP pipeline and control options for the technical slides

These are **proposed POC components**, not deployed controls. ONE would version the approved corpus and QA cases in Cloud Storage, then rerun the same case suite against both POC paths after a code/configuration change or an approved content snapshot change. An existing CI runner or manual script is sufficient; Cloud Build is one optional runner with configurable steps and triggers. If Cloud Build is chosen, the publishing workflow must explicitly start a run for CMS-only changes. Cloud Storage Object Versioning can retain previous object generations, though the case report should also record its source ID and version rather than relying on bucket history alone. [Cloud Build triggers](https://docs.cloud.google.com/build/docs/automating-builds/create-manage-triggers), [Cloud Build steps](https://docs.cloud.google.com/build/docs), [Cloud Storage Object Versioning](https://docs.cloud.google.com/storage/docs/object-versioning).

The proposed answer path runs in ONE's GKE application, using approved content, standalone Agent Retrieval as the current working default and direct RAG Engine as the POC comparison path. Model Armor can screen prompts and responses for prompt injection and sensitive content, but the application must enforce the screening result, source allowlist and citation checks. RAG Engine is listed as Preview in Singapore and its documented data-residency control is unsupported, so regional approval remains a selection gate. [Agent Retrieval overview](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/vector-search-2/overview), [RAG Engine overview and regions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/rag-overview), [Model Armor overview](https://docs.cloud.google.com/model-armor/overview).

For public access, the POC can apply Cloudflare WAF rules and Turnstile, with the token validated on the server through Siteverify. In the GKE API, an atomic shared counter store such as Memorystore for Redis can enforce per-session and IP burst limits, rolling hour/day limits, one in-flight answer, retry/token ceilings and an application-owned usage stop. The specific numbers, Cloudflare entitlements and added Memorystore cost need agreement. Test missing, expired and replayed tokens, direct origin access, parallel requests, shared office IPs and counter-store failure. Billing **alerts** by themselves do not cap usage. [Cloudflare rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/), [Turnstile Siteverify](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [Memorystore for Redis](https://docs.cloud.google.com/memorystore/docs/redis/memorystore-for-redis-overview), [Cloud Billing budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets).

Instrument the GKE application with OpenTelemetry spans around admission, retrieval, generation, screening and citation checks. Send trace and structured error/decision data to Cloud Trace and Cloud Logging, and create Cloud Monitoring dashboards and alerts for p95 time, error and refusal rates, 429s, quota-store health and content-withdrawal lag. Google documents managed OpenTelemetry collection for GKE as Preview, so confirm the selected collector path and its regional/security fit in the POC. Redact customer text and agree access and retention before enabling request-level review. [Managed OpenTelemetry for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/managed-otel-gke), [GKE OpenTelemetry deployment](https://docs.cloud.google.com/kubernetes-engine/docs/how-to/managed-otel-gke).

## Technical source check: security testing and Singapore status (28 September 2026)

**Promptfoo can test the actual POC API.** Its HTTP provider sends a configured request to an endpoint and extracts the answer with `transformResponse`; it can also parse a streamed response when its SSE parser matches the application's event format. The documented red-team sequence is `redteam init`, `redteam run` (generate plus evaluate), then `redteam report`. Save the configuration and generated cases, tag runs, rerun the same tests after changes, and add reviewed failure cases to the regression set. The report is triage evidence: Promptfoo says its model grader can produce false positives, and its interface permits review and correction of verdicts. [HTTP provider](https://www.promptfoo.dev/docs/providers/http/), [red-team configuration](https://www.promptfoo.dev/docs/red-team/configuration/), [grading review](https://www.promptfoo.dev/docs/red-team/troubleshooting/grading-results/), [repeat scans](https://www.promptfoo.dev/docs/red-team/model-drift/).

**Test the two injection surfaces separately.** Customer-input attacks can go through the normal API. Promptfoo's `rag-source-attribution` plugin probes invented source citations. Its `indirect-prompt-injection` plugin instead inserts adversarial text into a named retrieved-context template variable; that requires a test seam exposing that variable. To test the full retrieval path, Promptfoo documents poisoning controlled test documents, adding them to a test knowledge base, then scanning the application. A prompt-only HTTP endpoint does not by itself prove resistance to malicious source text. Keep the test corpus isolated and have QA inspect cited passages and any claimed exploit. [RAG red-team guide](https://www.promptfoo.dev/docs/red-team/rag/), [indirect injection plugin](https://www.promptfoo.dev/docs/red-team/plugins/indirect-prompt-injection/), [RAG poisoning workflow](https://www.promptfoo.dev/docs/red-team/plugins/rag-poisoning/), [source attribution plugin](https://www.promptfoo.dev/docs/red-team/plugins/rag-source-attribution/).

**The Singapore launch stages differ.** Google renamed Vector Search 2.0 to **Agent Retrieval**; its 5 March 2026 release note says Vector Search 2.0 is GA, and its current Agent Retrieval overview lists `asia-southeast1` among supported regions. This supports describing *standalone Agent Retrieval* as a GA service available in Singapore, subject to verifying the exact required features and security controls in the POC. Google's current *RAG Engine* region table separately labels `asia-southeast1` **Preview**. The GA status of the standalone retrieval service must not be transferred to the direct RAG Engine workflow. [Google product-name mapping](https://docs.cloud.google.com/gemini-enterprise-agent-platform/vertex-ai-name-changes), [GA release note](https://docs.cloud.google.com/vertex-ai/docs/core-release-notes), [Agent Retrieval supported regions](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/vector-search-2/overview), [RAG Engine region table](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/rag-overview).
